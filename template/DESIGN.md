# Design brief

Status: unselected product brief. This is a design-input template, not a finished interface or a visual QA result.

## When to use

Read and fill the relevant parts before a requested visual UI creation/redesign. A CLI/library change, prose edit or
state-only bug does not become visual redesign because frontend skills are present.

## Product decisions to record

- Audience and primary task:
- Supported surfaces, screen sizes and input methods:
- Information hierarchy and the most important action/state:
- Existing brand constraints, typography and asset ownership:
- Navigation, keyboard/focus, motion and accessibility requirements:
- Loading, empty, stale, partial, error, offline and success behavior:
- Data/state authority and destructive-action safeguards:
- Observed behavioral/rendered evidence and remaining limits:

Choose a concrete visual direction for the actual brief; no inherited robotics palette or framework is required.
Use semantic UI and truthful data states. Preserve existing functionality, state ownership and accessibility when polishing.
Rendered/browser checks apply only when authorized and useful to the changed surface. A generated minimal UI is not an approved visual design or a visual QA result.
